# UniJam Security Audit — 2026-07-15

> **Remediation update:** The findings below preserve the initial audit as historical evidence. The dated appendix at the end is the authoritative current assessment. The former Critical/High implementation findings and M-08 migration finding have been materially remediated, but the release decision remains **NO-GO** pending provisioned Cloudflare resources and real D1/Queue/live-provider and WebSocket revocation verification.

## Executive summary

**Overall risk: CRITICAL — do not deploy the pilot until the release blockers below are resolved and retested.**

The rebuilt tree has strong foundations: passkey RP/origin pinning, discoverable user-verified credentials, recovery sessions that do not count as recent passkey verification, opaque secure cookies, one-time hashed OAuth state with Spotify PKCE, short-lived Apple ES256 developer tokens, AES-256-GCM token envelopes with contextual AAD, an authenticated connector service boundary, provider URL allowlists, safe provider error mapping, legacy API gating, atomic Durable Object command/event/outbox persistence, stable command idempotency, and production-clean dependency audit results.

The principal unresolved risk is provider mutation idempotency. Queue redelivery or a Worker crash after a provider commits but before D1 persists the result can create duplicate playlists or append duplicate tracks. This directly violates the pilot stop condition for duplicate provider mutations. Live WebSocket actors also outlive D1 revocation and role changes, allowing a rotated guest or demoted co-host to retain the authority captured at connection time. These are release blockers.

Finding count: **1 Critical, 5 High, 9 Medium, 2 Low**, plus informational verification results.

## Release blockers

### C-01 — Publishing can duplicate provider mutations after redelivery or crash-after-commit

**Severity:** Critical
**Category:** CWE-362 / CWE-841; OWASP A04 Insecure Design
**Affected:** `connectors/queue.ts:96-120`, `connectors/queue.ts:160-190`, `connectors/storage.ts:182-230`, `connectors/router.ts:388-419`

The queue persists `in_flight`, performs the external mutation, and only then persists the provider result. If the provider creates the playlist or appends items and the Worker terminates before the following D1 write, the redelivered message sees `in_flight` and executes the same mutation again. The same problem exists with two simultaneous deliveries because `getPublishJob` plus `savePublishJob` has no revision compare-and-swap, lease, or single-writer authority. Reconfirming an existing operation also enqueues it again.

**Impact:** Duplicate private playlists and duplicate additions, including after an apparently successful operation. This violates the explicit zero-duplicate pilot requirement and must trigger a stop.

**Required remediation:** Serialize each destination operation or acquire a transactional lease with a fencing token/CAS revision. Never treat orphaned `in_flight` as permission to mutate again. Route orphaned attempts to reconciliation. For playlist creation, where provider idempotency keys are unavailable, persist a deterministic marker and reconcile by that marker or require operator recovery rather than replaying blindly. Add tests that terminate immediately after provider commit for both create and append, plus concurrent duplicate queue deliveries.

### H-01 — WebSocket sessions keep stale authority after revocation, expiry, invite rotation, or moderation

**Severity:** High
**Category:** CWE-613 / CWE-863; OWASP A01 Broken Access Control
**Affected:** `worker/room-durable-object.ts:492-497`, `worker/room-durable-object.ts:504-524`, `app/api/v1/rooms/[roomId]/invite/rotate/route.ts:20-31`, `app/api/v1/rooms/[roomId]/end/route.ts:15-24`, `worker/index.ts:85-89`

The WebSocket serializes the actor once and authorizes every later command from that attachment. Invite rotation and room ending revoke guest sessions only in D1. Moderation updates the DO snapshot and eventually D1, but does not update or close existing socket attachments. Session expiry is likewise never rechecked.

**Impact:** A guest with an already-open socket can continue after invite rotation/expiry; a demoted co-host can continue using host-authority actions with the stale `cohost` attachment.

**Required remediation:** Attach an opaque session identifier, expiry, invite epoch, and authority revision, then validate them on every command or maintain a DO-local revocation/authority table updated synchronously. Close matching sockets on rotation, end, leave, and moderation. Add regression tests for rotated guests, expired sessions, co-host demotion, and hibernation/resume.

### H-02 — No exact Origin / Fetch Metadata enforcement for cookie-authenticated WebSockets and unsafe HTTP methods

**Severity:** High
**Category:** CWE-352; OWASP A01 Broken Access Control
**Affected:** `worker/index.ts:33-43`, `lib/server/room-authority.ts:130-150`, `app/api/v1/auth/logout/route.ts:7-10`, `app/api/v1/rooms/[roomId]/end/route.ts:8-26`, `app/api/v1/rooms/[roomId]/invite/rotate/route.ts:10-37`, `app/api/v1/providers/[provider]/disconnect/route.ts:6-16`

The WebSocket upgrade authenticates target-host cookies without checking the browser `Origin`. State-changing routes also have no central exact-origin or `Sec-Fetch-Site` policy. `SameSite=Lax` is useful but does not protect against an untrusted sibling under the same registrable domain; production and staging are intentionally sibling origins.

**Impact:** A compromised or attacker-controlled `*.ashlr.ai` sibling could open an authenticated cross-origin WebSocket or issue same-site credentialed unsafe requests. Recent-passkey checks reduce the destructive window but do not remove it.

**Required remediation:** Enforce the exact environment origin for every WebSocket upgrade before cookie authentication. Add a Worker-wide unsafe-method guard requiring exact `Origin` and `Sec-Fetch-Site: same-origin`, with a deliberately documented exception only for provider callbacks that use independent state validation. Add negative tests from staging and another sibling subdomain.

### H-03 — Disconnect does not safely revoke in-flight publishing or immediately remove all private provider data

**Severity:** High
**Category:** CWE-613 / CWE-459; OWASP A01/A04
**Affected:** `connectors/router.ts:291-300`, `connectors/queue.ts:75-88`, `connectors/queue.ts:96-190`, `connectors/storage.ts:132-180`, `connectors/types.ts:67-79`

Disconnect deletes the encrypted connection and then flags stored jobs as cancelled. A queue invocation that already loaded and decrypted the connection can continue mutating the provider. There is no revocation generation/fencing check immediately before external mutations. Cancellation also leaves previews and publish records containing provider-specific private data; the store exposes no account-wide deletion or retention cleanup operation.

**Impact:** A provider mutation can occur after the user disconnects, and private provider data can remain beyond the promised immediate deletion semantics.

**Required remediation:** Serialize disconnect with publishing or increment a connection revocation generation and verify it immediately before every external mutation and after every response. Delete/anonymize previews, queued jobs, and private provider data on disconnect. Add connector retention/account-deletion cleanup and tests for disconnect during create, append, retry, and reconciliation.

### H-04 — D1 room projections retain detailed participant data after DO retention cleanup

**Severity:** High
**Category:** CWE-359; OWASP A02 Cryptographic Failures / privacy
**Affected:** `worker/room-durable-object.ts:550-561`, `worker/index.ts:98-108`

The 30-day DO alarm removes participants/events and sanitizes the DO snapshot, but it neither emits a sanitized projection nor deletes the corresponding D1 `room_projections` row. Scheduled cleanup removes projection receipts, not projections. The stale D1 snapshot can contain nicknames, suggestions, votes, and co-signatures indefinitely. There is also no complete account-deletion path coordinating room and connector erasure.

**Impact:** Detailed participant data outlives the documented 30-day retention period and deletion overrides.

**Required remediation:** Emit and project a sanitized recap snapshot or delete the D1 projection when the DO alarm runs. Add scheduled D1 cleanup keyed by `ended_at_ms`, account deletion, and provider-disconnect overrides. Test both primary and projected stores after retention expiry.

### H-05 — Shared invite exchange is unbounded and does not enforce lock state or pilot capacity

**Severity:** High
**Category:** CWE-400 / CWE-770; OWASP A04 Insecure Design
**Affected:** `app/api/v1/rooms/[roomId]/join/route.ts:8-30`, `lib/server/room-authority.ts:89-113`, `worker/room-durable-object.ts:209-210`, `worker/room-durable-object.ts:230-232`, `worker/room-durable-object.ts:430-453`

A valid shared capability can create unlimited guest sessions. There is no IP/capability exchange rate limit, active participant cap, or locked-room check before session insertion. Only guest `suggestion.stage` is blocked by lock. Each new session receives its own 60-command bucket while all actors share the 240-command room bucket, so an invite holder can create many sessions and exhaust the room-wide allowance.

**Impact:** Room denial of service, unbounded D1/DO growth, and joins/state access after a host believes the room is locked.

**Required remediation:** Rate-limit exchange by IP and capability fingerprint, cap active participants (25 for the pilot), enforce room lock before inserting a session, expire idle sessions, and design the room bucket so attacker-generated identities cannot starve the host.

## Medium findings

### M-01 — Request and WebSocket bodies are parsed before robust byte/depth limits

**Affected:** `lib/server/room-authority.ts:130-150`, `worker/room-durable-object.ts:504-509`, `lib/platform/protocol.ts:53-60`, `lib/platform/protocol.ts:63-85`, `app/api/v1/auth/recovery/route.ts:8-13`

Main-worker HTTP bodies are streamed to the DO without a byte cap, WebSocket messages are decoded and parsed without a raw-size limit, and `stableJson` recursively walks attacker-controlled values before enforcing 16 KiB. Very deep payloads can consume CPU or overflow recursion. Several auth endpoints also parse JSON before rate limiting.

**Fix:** Enforce `Content-Length` and streaming byte limits, raw WebSocket frame limits, maximum nesting/node counts, and rate checks before expensive parsing.

### M-02 — Occurrence and playback invariants are incomplete

**Affected:** `worker/room-durable-object.ts:203-207`, `worker/room-durable-object.ts:335-363`

`handoff.request` and `reaction.add` validate only ID syntax, not occurrence existence/status; provider and reaction values are arbitrary text. `queue.advance` can mark an occurrence played without host-confirmed playback, and repeated playback confirmations overwrite the timestamp. Co-hosts receive the same broad action set as hosts rather than persisted fine-grained authority.

**Fix:** Validate active occurrences, use provider/reaction enums, require confirmation before advancement, make confirmation one-way/idempotent, and persist an explicit co-host permission matrix.

### M-03 — Soft-deleted accounts can still authenticate with existing host sessions

**Affected:** `lib/server/host-session.ts:34-47`

The session query joins `accounts` but does not require `a.deleted_at_ms IS NULL`.

**Fix:** Add the deletion predicate and transactionally revoke sessions, passkeys, recovery codes, rooms, and provider state during account deletion.

### M-04 — Recovery creates a safe but unusable credential-replacement dead end

**Affected:** `app/api/v1/auth/recovery/route.ts:8-16`, `app/api/v1/auth/passkeys/additional/options/route.ts:8-15`, `app/api/v1/auth/passkeys/additional/verify/route.ts:9-21`

Recovery correctly creates a session that is not recent-passkey verified, but every additional-passkey endpoint requires a recent passkey. A host who lost all passkeys cannot replace one after consuming a recovery code.

**Fix:** Issue a narrowly scoped, single-use recovery-enrollment grant permitting exactly one new passkey; it must not authorize provider or destructive actions.

### M-05 — Malformed public API input can escape the required response envelope

**Affected examples:** `app/api/v1/auth/recovery/route.ts:8-16`, `app/api/v1/auth/passkeys/additional/options/route.ts:8-15`, `app/api/v1/auth/passkeys/additional/verify/route.ts:9-21`, `app/api/v1/migration/rooms/[legacyRoomId]/claim/route.ts:12-18`, `app/api/v1/rooms/[roomId]/end/route.ts:8-14`, `app/api/v1/rooms/[roomId]/invite/rotate/route.ts:10-16`

Several routes call `request.json()` or room-ID normalization outside a top-level safe parser/error boundary. Malformed JSON or invalid route input can become framework 500/non-envelope responses instead of `{data,error,requestId}`.

**Fix:** Centralize capped JSON parsing, validation, and a top-level route wrapper that maps all errors to stable, redacted codes.

### M-06 — Connector production/staging deployment resources are not defined in the repository

**Affected:** `wrangler.jsonc:29-84`; no connector Wrangler configuration exists

The web Worker binds services named `unijam-connectors-production` and `unijam-connectors-staging`, but the connector has no checked-in deployment configuration defining its D1 database, publish Queue/DLQ, secrets, analytics, or cleanup cron. Production/staging web D1 IDs are explicit sentinel placeholders at `wrangler.jsonc:40-45` and `wrangler.jsonc:67-72`.

**Fix:** Add isolated connector Wrangler configurations per environment, provision real resources, store secrets only through Cloudflare secret management, and fail CI/deploy when sentinel IDs or missing bindings remain.

### M-07 — Enrollment consumption is not atomic with account/passkey creation

**Affected:** `lib/server/passkeys.ts:174-229`

The challenge is consumed before WebAuthn verification. The enrollment code is then marked used in a separate D1 write before the account/passkey batch. A verification or batch failure can permanently burn a valid challenge or pilot code without creating the account.

**Fix:** Reserve/consume enrollment and insert the account/passkey in one transactional unit or implement rollback-safe reservation semantics. Consume the challenge after cryptographic verification using a one-time CAS.

### M-08 — Migration claim records provenance but does not import room state/history

**Affected:** `app/api/v1/migration/rooms/[legacyRoomId]/claim/route.ts:43-58`, `lib/server/legacy-migration.ts:19-29`

The claim sends only legacy room ID, export hash, and event count to `legacy.import`; it does not apply the exported settings, events, snapshot, or history. The API can report a claimed room even when `authorityClaimEventRecorded` is false. Export validation also uses recursive canonicalization before its 5 MB check and has no depth/node limit.

**Fix:** Validate and transactionally import a canonical, versioned snapshot/event model; verify the export hash in the authority; fail/roll back the claim if import fails; add structural limits and migration-hash/rollback tests.

### M-09 — Critical Worker integration tests do not run

**Affected:** `vitest.config.ts:4-14`, `tests/workers/room-durable-object.test.ts:1-3`, `worker/test-entry.ts`

`npm run test:workers` fails during module loading because `vinext/server/app-router-entry` attempts to resolve `virtual:vinext-rsc-entry`; zero tests are collected. The release's most security-sensitive concurrency and Durable Object behavior therefore lacks an executable CI gate.

**Fix:** Use a test entry that imports only the DO or provide the required Vinext virtual-module transform. Require worker tests in CI and add the C-01/H-01/H-05 concurrency and revocation cases.

## Low findings

### L-01 — CSP can be tightened

**Affected:** `lib/server/security-headers.ts:10-28`

The policy has strong defaults, framing denial, object denial, and production HSTS. Add `form-action 'self'` and `upgrade-insecure-requests`; minimize or nonce/hash the `style-src 'unsafe-inline'` allowance. Confirm any remotely hosted official brand asset origin is deliberately included rather than weakening `img-src` broadly.

### L-02 — Development dependency and update-age hardening remains

**Affected:** `.github/dependabot.yml:3-25`, `.npmrc:1-4`

The final full dependency audit reports four moderate findings in the older nested `esbuild` development chain used by `drizzle-kit`; the fix offered by npm would force a breaking downgrade to `drizzle-kit@0.18.1`. The earlier low `@babel/core` advisory was removed with a non-breaking lockfile update. The production-only audit reports zero vulnerabilities. Semgrep also noted missing Dependabot cooldowns and no npm minimum release age.

**Fix:** Upgrade/replace the affected development chain when compatible, add Dependabot cooldown policy, and set an appropriate `min-release-age` (for example seven days) with documented emergency overrides.

## Verified controls and prior findings resolved

- **Passkey origin/RP isolation:** production uses `unijam.ashlr.ai`; staging uses its separate origin and RP ID (`lib/server/passkeys.ts:45-56`).
- **Server-owned bootstrap identity:** registration creates the account ID server-side and requires a hashed, expiring, one-time enrollment code (`lib/server/passkeys.ts:58-77`, `lib/server/passkeys.ts:112-146`).
- **Passkey quality:** discoverable credentials and user verification are required; multiple credentials are supported (`lib/server/passkeys.ts:160-170`).
- **Authenticator counters:** assertion counter updates use compare-and-swap semantics (`lib/server/passkeys.ts:243-277`).
- **Recovery privilege separation:** recovery sessions have `passkey_verified_at_ms = NULL`, so they cannot satisfy recent-passkey gates (`lib/server/host-session.ts:16-31`, `lib/server/host-session.ts:57-59`).
- **Session cookie protection:** host and guest sessions use opaque `__Host-` cookies with `HttpOnly`, `Secure`, and `SameSite=Lax` (`lib/server/session-cookie.ts:1-18`).
- **Connector isolation:** the connector checks an internal service token and the web proxy supplies it; provider secrets are not exposed to the web UI (`connectors/router.ts:55-64`, `connectors/router.ts:189-194`, `lib/server/connector-proxy.ts:65-76`).
- **Token encryption:** provider tokens use versioned AES-256-GCM, random 96-bit IVs, 128-bit tags, non-extractable keys, and AAD bound to provider/account/connection/key version (`lib/providers/token-envelope.ts:58-65`, `lib/providers/token-envelope.ts:80-149`, `connectors/storage.ts:234-245`).
- **Spotify OAuth:** Authorization Code + PKCE S256, exact callback, hashed single-use state, and no client secret (`connectors/oauth.ts:6-58`, `connectors/oauth.ts:110-147`).
- **Apple Music:** short-lived ES256 developer tokens and US-storefront MUT validation before encrypted storage (`connectors/apple-music.ts:87-96`, `connectors/apple-music.ts:201-217`, `connectors/router.ts:246-289`).
- **SSRF resistance:** provider pagination validates the destination origin before follow-up fetches (`connectors/apple-music.ts:152-171`, `connectors/spotify.ts:143-168`).
- **Provider failure handling:** outbound calls have timeouts and provider failures are mapped to safe errors (`connectors/http.ts:12-48`).
- **Legacy API gating:** legacy room APIs require the disabled-by-default feature flag and migration secret (`lib/server/room-store.ts:103-108`); the old participant route checks this gate before access (`app/api/rooms/[roomId]/participants/route.ts:22-32`).
- **Migration ownership:** claims require both a recent passkey and the legacy host capability (`app/api/v1/migration/rooms/[legacyRoomId]/claim/route.ts:12-27`).
- **Room command atomicity:** command results, events, snapshot state, and local outbox records are committed in one DO SQLite transaction, and conflicting command-ID reuse is rejected (`worker/room-durable-object.ts:186-223`, `worker/room-durable-object.ts:404-425`).
- **Headers:** production responses receive CSP, HSTS, framing denial, MIME sniffing denial, restrictive referrer policy, and permissions policy (`lib/server/security-headers.ts:3-35`).
- **Secret scanning:** Gitleaks found no real secret in history. Current-tree matches were a test fixture value and ignored generated `dist` artifacts, not credentials.
- **Static analysis:** the repository Semgrep policy returned no application-code findings; broader rules returned only the supply-chain hardening items described in L-02.

## Remediation verification appendix — 2026-07-15 02:40 EDT

### Current decision

**NO-GO remains in effect, but not because a known Critical/High implementation vulnerability or M-08 migration defect remains open.** The focused re-audit found substantive remediation for C-01, H-01 through H-05, M-03, M-04, M-07, M-08, and M-09. M-06 is structurally remediated but deployment resources are still sentinel/unprovisioned. The remaining decision is an environment-provisioning and integration-assurance NO-GO, not a migration-code NO-GO.

Current residual release blockers:

1. `npm run validate:deploy:staging` correctly fails because both staging D1 bindings still use sentinel IDs (`wrangler.jsonc:67-72`, `wrangler.connectors.jsonc:69-74`). Production has the same unprovisioned state (`wrangler.jsonc:40-45`, `wrangler.connectors.jsonc:42-47`).
2. Provider concurrency/crash tests use the in-memory `MemoryStore`; there is not yet an executable D1 + real Queue concurrency test proving the fencing SQL under Cloudflare redelivery. Live Spotify/Apple Music behavior also remains credential-dependent.
3. D1-backed tests now prove per-message guest revocation, host logout/ownership revalidation, and invite-rotation closure. The local Cloudflare harness cannot preserve a client socket across `abortAllDurableObjects`, so authorization after a true hibernation/resume remains a remote staging assurance gate.
